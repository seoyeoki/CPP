# Module 00 디펜스 대비 노트

> 평가 한 달 전, 기억이 흐려졌을 때 이 문서부터 읽을 것. "왜 이렇게 짰는지"를 설명할 수 있어야 함.

---

## 1. 핵심 프레임워크 — 데이터 중심 사고

**모든 프로그램의 중심은 데이터다.** 절차지향과 객체지향의 차이는 "데이터를 어떻게 다루는가"의 차이일 뿐.

| | 절차지향 | 객체지향 |
|---|---|---|
| 데이터-함수 관계 | **독립** — 함수가 데이터를 매개변수로 받아서 처리 | **포함** — 데이터와 함수를 하나의 단위(클래스)로 묶음 |
| 접근 방식 | `함수(데이터)` | `객체.함수()` |
| 데이터 보호 | 없음 (누구나 직접 수정 가능) | `private`으로 캡슐화 가능 |

### OOP 4대 특성과 이 개념의 연결
- **캡슐화** = 데이터를 함수가 감싸서 보호하는 것 그 자체
- **추상화** = "어떻게(how)"는 숨기고 "무엇을(what)"만 노출 — 캡슐화가 있으면 자연히 따라오지만, **캡슐화 없이도 추상화만 단독으로 가능** (ex00이 그 예시)
- **상속/포함(합성) 구분** — "A가 B의 특수한 형태(is-a)"면 상속, "A가 B를 사용/소유(has-a)"면 포함. 판별법: **치환 테스트** — "B가 필요한 자리에 A를 넣어도 말이 되는가?" 안 되면 상속 아님
- **다형성** = 데이터 "값"이 아니라 객체의 "타입"에 따라 같은 호출이 다르게 동작하는 것 (값 분기 `if`와 헷갈리지 말 것)

> ⚠️ 함수 A가 함수 B를 내부에서 호출한다고 해서 상속 관계가 되는 게 아님. 그건 그냥 함수 재사용/합성. 상속은 오직 **클래스(타입) 사이의 관계**.

## 2. ex00 (Megaphone) — 왜 클래스를 안 썼는가

**"데이터가 중요하지 않아서" 클래스가 필요 없었다.** 캡슐화가 필요한 조건 두 가지:
1. 여러 번 호출 사이에 유지되는 상태가 있는가?
2. 보호해야 할 규칙(불변조건)이 있는가?

Megaphone은 인자를 받아 한 번 변환하고 끝 — **둘 다 해당 없음.** 그래서 클래스 없이 순수 함수(`toUpper`, `toUpperStr`)로 처리.

- **추상화는 있음**: `toUpperStr(argv)`를 부르는 쪽은 내부에서 어떻게 순회하고 어떻게 대문자로 바꾸는지 몰라도 됨. 이건 OOP 전유물이 아니라 일반 설계 원칙 — 클래스 없이도 추상화는 가능.
- **캡슐화는 없음, 그리고 없어도 됨.** 억지로 클래스를 씌우면 오히려 불필요한 장식(over-engineering).

### 예상 질문 대비
- **"왜 클래스를 안 만들었나요?"** → 위 논리 그대로 답변
- **`static_cast<unsigned char>`를 쓴 이유** → `char`가 signed일 때, UTF-8 등 non-ASCII 바이트가 음수로 해석될 수 있고, `std::toupper(int)`는 `EOF` 또는 `unsigned char` 범위 값만 유효 입력이라 음수를 넘기면 UB. 캐스팅으로 0~255 범위를 보장.
- **Makefile 증분 빌드** — `all`을 무작정 `.PHONY`로만 두면 매번 불필요하게 재링크됨. `all`은 `$(NAME)`에 위임만 하고, 실제 타겟(`$(NAME): $(OBJS)`)은 파일 타임스탬프로 관리되게 분리함.

## 3. ex01 (PhoneBook) — 왜 캡슐화가 필요한가

**Contact 데이터를 계속 저장해두고(지속 상태), 규칙을 지키며 접근해야 해서(불변조건)** 캡슐화가 필요했다.

- **지속 상태**: `PhoneBook`은 프로그램 실행 내내 최대 8개의 연락처를 들고 있어야 함
- **지켜야 할 규칙**: "8개 제한", "9번째부터 가장 오래된 것부터 교체", "연락처 필드는 비어있으면 안 됨" — 이런 규칙은 데이터를 `private`으로 감추고 정해진 함수로만 접근하게 해야 강제할 수 있음
- **추상화 + 캡슐화 둘 다 있음**: `addContact()`를 부르는 쪽은 내부 배열이 어떻게 순환하며 교체되는지 몰라도 됨 (추상화) + 그 배열 자체가 `private`이라 직접 못 건드림 (캡슐화)

### `PhoneBook` ↔ `Contact` 관계는 상속이 아니라 포함(has-a)
- `PhoneBook`이 `Contact`를 배열로 "가지고" 있는 것 — `Car`가 `Engine`을 갖는 것과 같은 구조
- 치환 테스트: "Contact가 필요한 자리에 PhoneBook을 넣어도 되나?" → 말이 안 됨 → 상속 아님

### 설계 세부사항 (질문 대비)
- **`Contact`에 기본 생성자가 필요했던 이유**: `PhoneBook`이 `Contact _contacts[8]`라는 고정 배열을 멤버로 가지므로, 배열 선언 시점에 각 칸을 기본 생성자로 초기화해야 함. 5개 인자짜리 생성자만 있으면 배열 자체가 컴파일 안 됨.
- **9번째 추가 시 교체 로직**: `_updateIndex = (_updateIndex + 1) % 8;` — 순환(modulo) 연산 하나로 "채우는 단계"와 "교체하는 단계"를 똑같은 코드로 처리 (별도 분기 불필요)
- **SEARCH 인덱스를 0~7로 통일한 이유**: 화면 표시(0~7)와 배열 접근(`_contacts[index]`)이 같은 숫자를 쓰게 만들어서 off-by-one 실수를 원천 차단
- **빈 슬롯도 그대로 보여주는 이유**: "최대 8개, 오래된 것부터 교체"는 스펙이 요구하는 **명시적 기능**이지 숨겨야 할 내부 구현 디테일이 아님 (9번째를 넣어보면 사용자도 어차피 알게 됨) → 별도의 "개수 추적" 없이 단순하게 설계
- **"다른 입력은 무시" = 완전히 침묵**: 스펙 문장의 병렬 구조(`ADD: ~한다 / SEARCH: ~한다 / ... / Any other input is ignored.`)를 볼 때, 안내 메시지조차 안 띄우는 게 더 정확한 해석이라 판단해 그렇게 구현
- **`const std::string &`로 매개변수를 받는 이유**: (1) 복사 비용 없음 (2) "이 함수는 원본을 안 바꾼다"는 의도 명시 (3) `const &`가 아니면 임시 객체(예: 문자열 리터럴에서 변환된 임시 `std::string`)를 못 받음 — 비-const 참조는 임시 객체(rvalue)에 못 붙는 언어 규칙 때문
- **`getSummarizedContact`/`getDetailedContact`에 `const` 붙인 이유**: 멤버를 안 바꾸는 함수임을 명시. `const` 함수 안에서는 `const`가 아닌 멤버 함수를 못 부름 (내부에서 `truncate()`도 `const`로 맞춰야 했던 이유)
- **`std::getline`을 쓴 이유 (`cin >>` 대신)**: `cin >>`는 공백에서 끊기고 빈 입력을 감지 못 함. "darkest secret"처럼 여러 단어 필드 + 빈 필드 검증이 필요해서 한 줄 전체를 읽는 `getline` 필수
- **`std::ostringstream`을 쓴 이유**: `setw`/`setfill`/`right` 같은 `<iomanip>` 조작자는 스트림에서만 동작. 결과를 화면이 아니라 `std::string`으로 반환해야 해서, "메모리에 쌓는 스트림"인 `ostringstream` 사용 (읽기 전용 `istringstream`이나 양방향 `stringstream`이 아니라, 쓰기만 하니 `ostringstream`이 정확한 선택)
- **`setw`는 1회성, `setfill`/`right`는 지속**: 컬럼마다 `setw`를 매번 다시 써야 함 (헷갈리기 쉬운 포인트)

### 일반 규칙 상기 (자세한 건 `RULES_CHECKLIST.md` 참고)
- 헤더엔 선언만, 구현은 `.cpp`에 (함수 템플릿 제외) — 안 지키면 해당 exercise 0점
- include guard 필수 — 안 지키면 전체 0점
- 헤더는 자기가 쓰는 의존성을 직접 include (다른 헤더가 대신 include 해준 것에 의존하면 안 됨)
- STL은 Containers(vector 등) + `<algorithm>`만 금지, `<string>`/`<iostream>`/`<sstream>`/`<iomanip>`/`<cctype>`은 자유롭게 사용 가능
- Orthodox Canonical Form은 **Module 02부터** 필수 — 00/01은 해당 없음 (다음 모듈부터 4대 특수 함수 직접 챙겨야 함)

## 4. 자주 헷갈렸던 것들 (다시 안 헷갈리게)

- **UB(정의되지 않은 동작)** ≠ "언더플로우". `char` 부호 문제는 연산 결과가 범위를 넘은 게 아니라, 애초에 타입이 그 값을 못 담아서 생기는 문제 → "부호 표현 문제"가 정확한 용어
- **`Type::name`은 "조회"(스코프 지정), `Type name`은 "선언"** — 계속 헷갈렸던 패턴. `std::string::firstName`처럼 쓰면 "string 안에서 firstName을 찾아라"가 되어버림
- **함수 순서는 상관없음, 단 "호출 전에 선언이 보여야" 함** — 이건 C/C++ 공통 원칙이지 멤버 함수만의 특별한 규칙이 아님. 헤더의 선언을 미리 include했다면 실제 구현(정의)은 파일 어디에 있어도 됨
- **참조(`&`)는 포인터를 편하게 쓰는 문법**이지 새로운 개념이 아님 — C의 포인터가 하던 일(주소로 원본 다루기)을 `&`/`->` 없이 쓰게 해주는 것뿐
